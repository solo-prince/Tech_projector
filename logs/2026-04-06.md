## 🚀 Project Update - Atlas V3 Robotic Manipulator

**Date:** 2026-04-06

**Progress:**
- Completed initial integration and calibration of all six servo motors (shoulder, elbow, wrist roll/pitch/yaw, and gripper).
- Implemented basic forward kinematics (FK) logic in the control software to calculate end-effector position based on joint angles.
- Conducted initial stress testing on the mechanical structure under a 500g load to identify potential weak points in the 3D-printed components.

**Technical Work:**
- **Hardware:** Assembled the final V3 chassis using PLA+ for structural rigidity. Replaced the standard MG996R servos with high-torque, metal-geared DS3218 servos on the shoulder and elbow joints to handle increased load requirements.
- **Microcontroller:** Ported the control logic from a simple Arduino Uno to an ESP32-S3 to leverage its higher processing speed and additional PWM channels for smoother servo control.
- **Software Logic:** Developed a Python script to calculate FK based on the Denavit-Hartenberg (DH) parameters of the arm's geometry. The script sends joint angle commands via serial communication to the ESP32 firmware, which uses the `ESP32Servo` library for precise PWM control.

**Issues & Fixes:**
- **Issue:** Experienced significant "jitter" and position drift in the shoulder and elbow joints when under load. This was particularly noticeable when attempting precise movements.
- **Root Cause:** The power supply for the servos was shared with the ESP32 logic. The high current draw during movement caused voltage drops on the power rail, leading to brownouts and inconsistent PWM signals.
- **Fix:** Implemented a separate 5V 10A power supply dedicated solely to the servo rail. Added large electrolytic capacitors (1000uF) across the servo power lines to mitigate voltage spikes during high current draw.

**Next Steps:**
- Begin development of the Inverse Kinematics (IK) solver to allow control via target coordinates (x, y, z) rather than individual joint angles.
- Integrate the force sensor feedback from the gripper to implement object detection and grip force limitation.

## 🚀 Project Update - Acoustic Guard Edge ML

**Date:** 2026-04-06

**Progress:**
- Successfully deployed a fully quantized TensorFlow Lite Micro (TFLite Micro) model to the ESP32-S3 microcontroller for real-time sound event detection.
- Completed initial testing of model performance on a dataset of common household sounds (glass breaking, smoke alarm, dog barking).
- Integrated the microphone data pipeline, including audio sampling, pre-processing (MFCC extraction), and inference.

**Technical Work:**
- **Hardware:** Utilized an ESP32-S3-DevKitC-1 with an external I2S MEMS microphone (PDM interface) for high-quality audio capture.
- **Model Optimization:** The original Keras model (trained on a PC) was 32-bit floating-point (2.1 MB). Using TFLite Micro's post-training quantization tools, we converted the model to 8-bit integer precision. This reduced the model size to 512 KB, allowing it to fit entirely within the ESP32's internal RAM.
- **Inference Pipeline:** The C++ firmware captures 1-second audio snippets, calculates Mel-Frequency Cepstral Coefficients (MFCCs) in real-time, and feeds them into the TFLite interpreter for classification. Inference time for a 1-second snippet is consistently under 100ms.

**Issues & Fixes:**
- **Issue:** Initial attempts to run the unquantized model resulted in frequent crashes and "out of memory" errors on the ESP32.
- **Root Cause:** The model size exceeded the available heap memory for the microcontroller, and floating-point calculations were too slow for real-time performance.
- **Fix:** Implemented full integer quantization (int8) for the model weights and activations. Additionally, optimized the pre-processing logic to reduce memory allocations during the MFCC calculation loop.

**Next Steps:**
- Integrate the model output with an MQTT client on the ESP32 to send alerts to a central home automation hub (e.g., Home Assistant).
- Expand the model's training dataset to include additional sound events and test robustness against ambient noise.

## 🚀 Project Update - EnviroSense Data Logger

**Date:** 2026-04-06

**Progress:**
- Finalized hardware integration of multiple sensors for a robust environmental monitoring system.
- Developed the data ingestion script on the central Raspberry Pi 4 to collect time-series data from all connected sensors.
- Completed initial setup of the InfluxDB database for high-volume data storage and retrieval.

**Technical Work:**
- **Hardware:** Connected multiple sensors (BME280 for temp/humidity/pressure, BH1750 for lux levels) to a Raspberry Pi Pico acting as a data collection hub. The Pico communicates with the central Raspberry Pi 4 via UART.
- **Data Pipeline:** The Python script on the Pi 4 uses the `pyserial` library to read data packets from the Pico. The script parses the incoming JSON string, validates the sensor readings, and formats them for entry into the InfluxDB time-series database.
- **Automation Logic:** Implemented a systemd service to ensure the data ingestion script runs continuously and automatically restarts upon system boot or failure.

**Issues & Fixes:**
- **Issue:** Intermittent data corruption and "checksum failed" errors were observed during high-frequency data logging. The data packets from the Pico were occasionally truncated.
- **Root Cause:** The UART communication between the Pico and Pi 4 was susceptible to noise and timing issues. The Pi 4's high-level Python script sometimes missed parts of a packet due to buffering.
- **Fix:** Implemented a robust data validation and re-synchronization protocol on both the Pico and Pi 4. The Pico now wraps data packets with start/end markers, and the Pi 4 waits for complete packets before processing to prevent partial reads.

**Next Steps:**
- Develop a web-based visualization dashboard using Grafana to display real-time and historical sensor data from InfluxDB.
- Configure alert triggers based on predefined thresholds (e.g., send an email alert if humidity exceeds 70%).
