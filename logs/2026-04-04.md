## 🚀 Project Update - Autonomous Rover Platform (v2)

**Date:** 2026-04-04

**Progress:**
- Completed integration and initial calibration of the LiDAR and IMU modules on the rover chassis.
- Successfully performed initial odometry and mapping tests in the controlled test environment using ROS.
- Implemented basic teleoperation functionality and tested motor control response to high-level commands.

**Technical Work:**
- **Sensor Integration:** Installed an RPLidar A1M8 and an MPU6050 IMU. Developed a ROS node to handle sensor data acquisition and publish to the `scan` and `imu` topics.
- **Odometry Implementation:** Used the `robot_localization` package (specifically the `ekf_localization_node`) to fuse data from the wheel encoders, IMU, and LiDAR. The EKF (Extended Kalman Filter) configuration was tuned to prioritize IMU data for short-term rotation and wheel encoders/LiDAR for long-term position updates.
- **Motor Control:** Refined the low-level motor control node to handle velocity commands (twist messages) from ROS. Implemented a basic PID controller on the individual motor drivers (using an ESP32 as the low-level controller) to ensure accurate wheel velocity tracking.

**Issues & Fixes:**
- **Odometry Drift:** Initial EKF implementation showed significant position drift over longer distances, particularly during turns.
    - *Fix:* Debugged the EKF configuration file. Identified incorrect noise covariance values for the IMU and wheel encoders. Adjusted the covariance matrix based on empirical testing data to better reflect sensor uncertainty. Implemented a static bias calibration routine on the IMU startup.
- **Motor Noise:** High-frequency noise from the motors interfered with the IMU readings when close together.
    - *Fix:* Implemented a low-pass filter on the IMU data before feeding it into the EKF to remove high-frequency noise caused by motor PWM.

**Next Steps:**
- Begin development of the path planning and obstacle avoidance algorithms (A* and DWA).
- Integrate the navigation stack with the existing sensor fusion and control loops.
- Conduct thorough real-world testing in unstructured environments to validate localization accuracy.

## 🚀 Project Update - Smart Greenhouse System

**Date:** 2026-04-04

**Progress:**
- Completed deployment of all three ESP32-based sensor nodes to monitor soil moisture, ambient temperature, and humidity across different zones of the greenhouse.
- Established a robust MQTT connection from all nodes to the central broker.
- Successfully visualized real-time data on the Grafana dashboard.

**Technical Work:**
- **Hardware:** Deployed custom PCBs with ESP32-WROOM-32 modules, capacitive soil moisture sensors (instead of resistive, to avoid corrosion), and DHT22 temperature/humidity sensors.
- **Firmware:** Developed firmware using PlatformIO/Arduino framework. Implemented deep sleep functionality on the ESP32 to conserve power, waking up every 15 minutes to take a reading and publish data. The data payload is structured as JSON.
- **Network Protocol:** Utilized the lightweight MQTT protocol for data transmission. Configured the central Raspberry Pi broker (Mosquitto) to handle subscriptions and forwarding to an InfluxDB database.
- **Visualization:** Configured Grafana to query the InfluxDB database and display real-time time-series data for each sensor node.

**Issues & Fixes:**
- **Network Instability:** Encountered intermittent Wi-Fi connectivity issues for one of the sensor nodes located at the far end of the greenhouse. The metal support structure caused significant signal attenuation.
    - *Fix:* Switched the node's Wi-Fi channel and added a reconnection logic with exponential backoff to ensure reliable data transmission even after short disconnections. Adjusted antenna positioning to minimize metal interference.
- **Deep Sleep Issues:** Initial deep sleep implementation caused the ESP32 to occasionally restart unexpectedly.
    - *Fix:* Identified a memory leak issue in the sensor initialization code that caused instability when re-initializing after wake-up. Refactored the code to ensure proper memory management during the deep sleep cycle.

**Next Steps:**
- Implement basic automation logic on the central server (Node-RED) to control irrigation pumps based on soil moisture thresholds.
- Add a new sensor node to monitor ambient light levels.
- Develop a user interface for manual overrides and system configuration.

## 🚀 Project Update - Edge Predictive Maintenance System

**Date:** 2026-04-04

**Progress:**
- Completed training and initial evaluation of the anomaly detection model (Autoencoder) on simulated motor vibration data.
- Successfully converted the model to TensorFlow Lite and deployed it to the target embedded platform (Raspberry Pi 5).
- Established real-time inference pipeline from sensor data acquisition to anomaly score calculation on the edge device.

**Technical Work:**
- **Model Architecture:** Designed and trained a sparse Autoencoder using Keras/TensorFlow. The model learns a compact representation of healthy motor vibration patterns. Anomaly detection is performed by calculating the reconstruction error; high error indicates anomalous behavior.
- **Data Preprocessing:** Implemented a feature extraction pipeline using Python/Pandas. Raw vibration data (time series) is processed using Fast Fourier Transform (FFT) to extract frequency-domain features (power spectral density) for model input.
- **Edge Deployment:** Used the TensorFlow Lite Converter to quantize the model from FP32 to INT8 precision. This reduces the model size by ~75% and significantly improves inference speed on the Raspberry Pi's CPU. Developed a Python script for real-time inference using the `tflite_runtime` library.

**Issues & Fixes:**
- **Inference Latency:** Initial inference latency on the Raspberry Pi 5 was ~150ms per prediction, too slow for real-time monitoring of high-speed machinery.
    - *Fix:* The initial model was unnecessarily complex. Reran training with a smaller latent space and fewer hidden layers in the Autoencoder. Retrained and re-quantized the optimized model. The final inference latency dropped to <40ms per prediction.
- **Data Drift:** The model's accuracy degraded when tested on new data collected under slightly different operating conditions (e.g., higher load).
    - *Fix:* Updated the training pipeline to include a wider range of healthy operating conditions in the training dataset. Implemented a data augmentation technique during training to simulate minor variations in operating parameters.

**Next Steps:**
- Integrate the Raspberry Pi with the actual industrial accelerometer (ADXL345) via SPI communication.
- Configure communication protocols (e.g., MQTT) to send alerts to a central monitoring dashboard when anomalies are detected.
- Begin collecting real-world baseline data from healthy equipment to retrain the model with actual production data.
